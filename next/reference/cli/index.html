CLI

Command-line client for OCIDex.

Commands are noun then verb: ocidex-cli sbom push, ocidex-cli registry list.

Configuration is resolved in this order, most specific first: command-line flag, environment variable, ~/.config/ocidex/config.yaml, built-in default. The API key is deliberately not a flag — see docs/adr/0029-cli-design.md.

Global flags

Section titled “Global flags”

Every command accepts these.

Flag Default Description
-o, --output output format: table, json, or yaml (config output, default table)
--server OCIDex base URL (env OCIDEX_URL, config server, default http://localhost:8080)

ocidex-cli agent

Section titled “ocidex-cli agent”

Create keys for agents such as ocidex-mcp.

An agent key belongs to you but is limited to a preset, to named namespaces and to an expiry, and the writes it may make can wait for your approval in the web UI. To connect an MCP client in one step, use ocidex-cli mcp install.

ocidex-cli agent create

Section titled “ocidex-cli agent create”

Create an agent key.

Presets: analyst reads everything in its namespaces, private data included; changes nothing remediation as analyst, and may manage your watchlist coverage as analyst, and may ask for scans; each scan waits for your approval

The key is printed once, on stdout, and never again.

Flag Default Description
--expires-in 720h0m0s stop the key working after this long; at most 2160h (90 days)
--label the client using the key, shown in the audit log and approvals (e.g. “Claude Code on laptop”)
--name human-readable label for the key (required)
--namespace namespace the agent may work in, by name or id, repeatable (default: your only namespace)
--preset analyst what the agent may do: analyst, remediation, coverage

ocidex-cli approval

Section titled “ocidex-cli approval”

See agent requests waiting for approval.

Approving and denying happen only in the web UI, signed in: no key can approve, or an agent holding one could approve itself. These commands list the requests and take you to the page that decides them.

ocidex-cli approval list

Section titled “ocidex-cli approval list”

List agent requests

Flag Default Description
--status pending only requests in this status: pending, approved, denied, expired, executed, failed (empty for all)

ocidex-cli approval open

Section titled “ocidex-cli approval open”

Open a request’s approval page in the browser

ocidex-cli artifact

Section titled “ocidex-cli artifact”

Work with tracked artifacts

ocidex-cli artifact changelog

Section titled “ocidex-cli artifact changelog”

Show what changed between successive versions of an artifact.

An artifact usually has several SBOMs per version — one per architecture and flavor — so a changelog only means something once that axis is pinned. Pass –arch and –flavor when the artifact has more than one; the available values are printed to stderr in table mode.

The history is paged, newest first: an artifact with a thousand versions has a thousand transitions and each one carries a full component diff. Page back through it with –offset.

Flag Default Description
--arch architecture to follow, e.g. amd64
--flavor image flavor to follow, e.g. distroless
--limit 0 maximum transitions to return (server default 20)
--offset 0 transitions to skip, counting back from the newest
--subject-version compare only within this version

ocidex-cli artifact get

Section titled “ocidex-cli artifact get”

Show one artifact in full

ocidex-cli artifact license-summary

Section titled “ocidex-cli artifact license-summary”

Count components by license across an artifact’s latest SBOM

ocidex-cli artifact list

Section titled “ocidex-cli artifact list”

List tracked artifacts.

The SBOMS column reads sufficient/total: the server hides artifacts with no sufficiently enriched SBOM unless –include-insufficient is given.

Flag Default Description
--include-insufficient also list artifacts whose SBOMs are not sufficiently enriched
--limit 0 maximum artifacts to return (server default 50)
--name filter by artifact name
--offset 0 index of the first artifact to return
--type filter by CycloneDX type, e.g. container or application

ocidex-cli component

Section titled “ocidex-cli component”

Search the packages found inside SBOMs.

There are two views of the same data, because the server offers two and they answer different questions. list is deduplicated: one row per distinct package, with the number of SBOMs it appears in — use it to browse. search is per-occurrence: one row per SBOM a named package appears in, with the version that SBOM carries — use it to answer “who ships the vulnerable version”.

ocidex-cli component get

Section titled “ocidex-cli component get”

Show one package occurrence in full.

The id is a component id from component search, which identifies the package inside one SBOM — hashes, licenses, and external references are all that SBOM’s view of it.

ocidex-cli component list

Section titled “ocidex-cli component list”

Browse distinct packages across every visible SBOM.

One row per distinct package, not per occurrence: VERSIONS and SBOMS say how many of each are behind it. Run component purl-types for the values –purl-type accepts.

Flag Default Description
--group filter by package group, e.g. a Maven groupId
--limit 0 maximum packages to return (server default 50)
--name filter by package name (substring match)
--offset 0 index of the first package to return
--purl-type filter by purl type, e.g. golang, npm, deb
--sort sort field (server default: name)
--sort-dir sort direction: asc or desc
--type filter by CycloneDX component type, e.g. library

ocidex-cli component purl-types

Section titled “ocidex-cli component purl-types”

List the purl types present in visible SBOMs.

These are the values component list --purl-type accepts; they depend on what has actually been ingested, not on a fixed vocabulary.

ocidex-cli component search

Section titled “ocidex-cli component search”

Find every SBOM a named package appears in.

One row per occurrence, so the same package appears once per SBOM that carries it, with that SBOM’s version. The name is matched by the server, not globbed here.

Flag Default Description
--group filter by package group, e.g. a Maven groupId
--limit 0 maximum occurrences to return (server default 50)
--offset 0 index of the first occurrence to return
--version filter to one version

ocidex-cli component versions

Section titled “ocidex-cli component versions”

Show which version of a package each artifact carries.

This is the drift question: one row per artifact shipping the named package, with the version it has. Unpaginated — the server returns the whole set.

Flag Default Description
--group filter by package group, e.g. a Maven groupId
--type filter by CycloneDX component type, e.g. library
--version filter to one version

ocidex-cli job

Section titled “ocidex-cli job”

Inspect the registry scan queue.

A job is one attempt to pull an image and catalog it. Jobs are created by the scanner, not by this CLI; what you can do here is watch them and, as an admin, put a failed one back in the queue.

ocidex-cli job get

Section titled “ocidex-cli job get”

Show one scan job in full.

The fields that matter on a failure are LAST ERROR and ATTEMPTS: the queue retries on its own, so a job with several attempts and a stable error is stuck rather than merely slow.

ocidex-cli job list

Section titled “ocidex-cli job list”

List scan jobs, newest first.

Without –state this lists every state, including the succeeded jobs that make up most of the queue’s history. –state failed is the one worth watching.

Flag Default Description
--limit 0 maximum jobs to return (server default 50)
--offset 0 index of the first job to return
--state filter by state: queued, running, succeeded, or failed

ocidex-cli job retry

Section titled “ocidex-cli job retry”

Put a failed scan job back in the queue.

Admin-only. The server returns no body, so success is silent; re-run job get &lt;id&gt; to see the job back in the queued state.

ocidex-cli key

Section titled “ocidex-cli key”

Manage your API keys.

Every subcommand here needs an existing key, so the first one has to come from the web UI. After that a key can mint its successors.

ocidex-cli key create

Section titled “ocidex-cli key create”

Create an API key.

The key is printed once, on stdout, and never again. Everything else this command says goes to stderr, so ocidex-cli key create --name ci &gt; key.txt captures exactly the key and nothing else.

Capabilities are a ceiling, not a grant: the key can never do more than your namespace roles allow, and a role change narrows every key you hold without any key change. Omitting –capability asks for all of them, which resolves to exactly what you can do. Name them where something narrower will do: a key that only ingests cannot delete an SBOM even where you can.

–expires-in makes the key stop working after that long (for example 720h). Without it the key works until revoked.

Flag Default Description
--capability capability this key may exercise, repeatable (default: all of them)
--expires-in 0s stop the key working after this long, e.g. 720h (default: never)
--name human-readable label for the key (required)

ocidex-cli key delete

Section titled “ocidex-cli key delete”

Revoke an API key.

Takes the key’s UUID, which key list shows — not the key itself, which you are not expected to still have.

ocidex-cli key list

Section titled “ocidex-cli key list”

List your API keys.

Only metadata: the key itself is stored hashed and cannot be shown again. PREFIX is what identifies a key in the audit log.

ocidex-cli login

Section titled “ocidex-cli login”

Save a server URL and API key to the config file.

Prompts for whatever is not given as a flag, verifies the key by asking the server who you are, and only then writes ~/.config/ocidex/config.yaml with mode 0600. A key that does not work is rejected here rather than at the next command.

–key exists for non-interactive setup, but prefer OCIDEX_API_KEY in CI: an argument is visible in the process table and in most runners’ command logs.

Flag Default Description
--key API key (prompted when omitted; prefer OCIDEX_API_KEY in CI)
--server-url server to log in to (prompted when omitted)

ocidex-cli logout

Section titled “ocidex-cli logout”

Remove the stored API key.

Only the key: the server URL and output preference are settings, not credentials, and re-typing them after every logout is friction with no security benefit. The file is deleted outright once nothing is left in it.

This does not revoke the key server-side — use key delete &lt;id&gt; for that.

ocidex-cli mcp

Section titled “ocidex-cli mcp”

Connect MCP clients to OCIDex

ocidex-cli mcp install

Section titled “ocidex-cli mcp install”

Register ocidex-mcp with an MCP client (Claude Code, Claude Desktop or Cursor).

This creates an agent key for the client (see ocidex-cli agent create) and writes it into the client’s user-wide MCP configuration, so the client never runs with your personal login key. The key is written only to that file, which is kept readable by you alone; it is never printed.

Running it again changes nothing while OCIDex is already registered for this server. –rotate creates a fresh key and replaces the old one in the file; revoke the old key afterwards under Admin → Agents.

Flag Default Description
--client claude-code the MCP client: claude-code, claude-desktop, cursor
--config the client’s config file (default: the client’s user-wide file)
--expires-in 720h0m0s stop the key working after this long; at most 2160h (90 days)
--label the client using the key, shown in the audit log and approvals (e.g. “Claude Code on laptop”)
--name the key’s name (default “mcp: <client>”)
--namespace namespace the agent may work in, by name or id, repeatable (default: your only namespace)
--preset analyst what the agent may do: analyst, remediation, coverage
--rotate create a new key even if OCIDex is already registered

ocidex-cli namespace

Section titled “ocidex-cli namespace”

Manage namespaces.

A namespace owns sources and everything ingested through them, and its visibility governs who can read those artifacts (ADR-039).

Every command that takes a namespace accepts either its UUID or its name; a name is resolved through /api/v1/namespaces/by-name before the call.

ocidex-cli namespace create

Section titled “ocidex-cli namespace create”

Create a namespace.

Visibility defaults to private, so a namespace created without –visibility is readable only by its owner.

ocidex-cli namespace create –name acme –visibility public

Flag Default Description
--name namespace name, unique across the server
--visibility who can read artifacts under it: public or private (default private)

ocidex-cli namespace delete

Section titled “ocidex-cli namespace delete”

Delete a namespace and everything ingested under it

Flag Default Description
-y, --yes do not prompt for confirmation

ocidex-cli namespace get

Section titled “ocidex-cli namespace get”

Show one namespace in full

ocidex-cli namespace list

Section titled “ocidex-cli namespace list”

List visible namespaces

ocidex-cli namespace update

Section titled “ocidex-cli namespace update”

Rename a namespace or change its visibility.

Both fields are omit-to-keep on the API’s PATCH, so only the flags actually given are sent — no read-modify-write, and nothing else can be reset by accident.

Flag Default Description
--name new namespace name
--visibility new visibility: public or private

Omitting –namespace gives the registry a namespace of its own, named after it. Pass an existing namespace to put several sources under one owner and one visibility setting.

ocidex-cli source

Section titled “ocidex-cli source”

Manage ingest sources.

A source is one ingest channel into a namespace (ADR-039). create makes an upload source, the kind SBOMs are pushed to directly; an OCI registry source is created with ocidex-cli registry create, which configures the registry behind it at the same time.

Sources are named uniquely only within their namespace, so the API offers no by-name lookup for them: these commands take a source UUID, which ocidex-cli source list prints.

ocidex-cli source create

Section titled “ocidex-cli source create”

Create an upload source in a namespace.

An upload source has nothing to configure: it is the channel SBOMs pushed with ocidex-cli sbom push are attributed to.

ocidex-cli source create –name ci-uploads –namespace acme

--namespace owning namespace, by id or name
