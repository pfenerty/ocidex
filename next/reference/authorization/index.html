Authorization matrix

Every registered API operation and the single rule that decides whether a caller may invoke it. The table is generated by joining the live huma spec against the authRules declarations in internal/api/authclass.go, so it cannot drift from the router: make check fails if this file is stale, and the conformance test in internal/api/authclass_test.go fails if an operation is registered without a declaration or a declaration outlives its operation.

Auth classes

Section titled “Auth classes”
Class Meaning
public No credentials required. Rows the caller may not see are removed by a VisibilityFilter in SQL, so an anonymous caller gets a narrower answer rather than a 403.
secret Authenticated by a per-resource shared secret in the request, not by a user identity.
authenticated Any authenticated principal, viewer included. RequireAuthenticated.
member member or admin; viewer is rejected with 403. RequireMember.
admin admin only; everyone else gets 403. RequireAdmin.
capability A caller whose role in the namespace the resource hangs from grants the capability in the Capability column, or an admin. Per ADR-039 the namespace is the only authorization anchor — sources and registries inherit their answer from the namespace above them. Enforced by RequireCapability or, where the namespace is only knowable from the request, in the handler; the Notes column says which. The capability each role grants is in the table below.

Namespace roles and capabilities

Section titled “Namespace roles and capabilities”

A capability operation asks whether the caller’s role in the namespace the resource hangs from grants the capability it declares. An installation-wide admin short-circuits every cell; an installation-wide viewer is capped at read_private whatever role a namespace gave them; a non-member holds nothing (ADR-046).

Write scope

Section titled “Write scope”

The Write column is orthogonal to the class. A ✓ means the operation also declares RequireWrite, which rejects (403) an API key whose declared capabilities are all read-only, even when the key’s owner passes the class check. It is a coarse gate: the Capability column is what narrows an individual operation, and a key is refused there unless it declares that capability and its owner’s role grants it. Session cookies carry no ceiling and are unaffected.

Declared in authRules but not registered above, because the matrix is generated from a router built without a development config. These operations do not exist in a production build — they are absent from the route table and from web/openapi.json, not merely refused at runtime.

Operation Class Capability Write Notes
dev-mint-session public — POST /api/v1/dev/session. Development builds only; not registered when ENVIRONMENT != development. Mints a real session cookie for a persona seeded by scripts/dev-auth.sh.
