Upgrade

OCIDex follows semantic versioning. What counts as a breaking change, and what the 1.x line promises, is in ADR-052. What changed in each release is in the changelog. Anything you must do to upgrade is on this page.

Supported upgrade paths

Section titled “Supported upgrade paths”
From To Path
Any 1.x Any later 1.x Direct. No intermediate stops.
Latest 0.x minor 1.0 Direct.
Older 0.x 1.0 Upgrade to the latest 0.x minor first, then to 1.0.
Any version An older version Not supported as an upgrade. Restore a backup instead (see Rolling back).

The API, the scanner, every enricher and the vulnerability worker must run the same version. Mixed versions are only supported during a rolling upgrade. Upgrade the inventory agent, the operator and ocidex-cli along with the server.

Before every upgrade

Section titled “Before every upgrade”
  1. Read the release’s notes under Per-version notes, and do any step marked before upgrading first. Skipping some of them stops the new version from starting.
  2. Back up the database (see Back up and restore). Rolling back means restoring this backup. Back up the Secret too: a database restored without its encryption keys has unreadable registry credentials.
  3. Note the current revision with helm history <release> -n <ns>, so you know what to roll back to.

It’s also a good moment to re-read the production checklist, since releases add settings to it.

What happens during an upgrade

Section titled “What happens during an upgrade”

Migrations run before any new pod serves traffic. With the chart, the migrate Job is a pre-install,pre-upgrade hook: it runs ocidex migrate up, then ocidex migrate encrypt-secrets, and the Deployments are updated only after it succeeds. Without the chart, run both with the new binary before you replace the running processes.

Each migration runs in its own transaction, so a failure leaves the schema at the last one that succeeded. The exception is an index built with CREATE INDEX CONCURRENTLY, which can leave an INVALID index behind; drop it before retrying.

If the migrate Job fails

Section titled “If the migrate Job fails”
  • The upgrade fails, the Deployments are not updated, and the previous version keeps serving. Fix the cause promptly: how well it works against a partly migrated schema depends on how far the migration got.
  • Read the Job’s logs: kubectl -n <ns> logs job/<release>-migrate-<revision> --all-containers. The pods are cleaned up a few minutes after a failure. If the logs are gone, run ocidex migrate audit in a throwaway pod: it repeats the ownership check, read-only.
  • Common causes are in Troubleshooting.
  • Then run the same upgrade again. migrate up resumes where it stopped.

Following releases with Flux

Section titled “Following releases with Flux”

With Flux, a HelmRelease that names a version range follows new charts as they’re published:

A released chart pins every image by digest, so a chart version always means the same images. Leave image.tag unset; setting it overrides those digests.

Every push to main also publishes a chart, versioned 0.1.0-main.<build>.<sha>. A range of ">=0.0.0-0" follows those, for a preview installation that tracks main.

Before you widen the range to a new minor or major, read its notes below.

Rolling back

Section titled “Rolling back”

The supported rollback is restoring the pre-upgrade backup and redeploying the previous version.

  1. Scale every OCIDex Deployment to zero, or suspend the HelmRelease (flux suspend helmrelease ocidex -n flux-system).
  2. Restore the database from the backup you took before upgrading (see Back up and restore).
  3. Redeploy the previous version: helm rollback <release> <revision> -n <ns>, or pin the previous chart version in the HelmRelease and resume it. Remove the pin once a fixed release is out, or Flux will hold the version there.

Anything ingested after the backup is lost, so re-push those SBOMs or re-run the scans.

A chart rollback alone does not roll back migrations. Migrations add columns and tables more often than they remove them, so the previous version usually runs against the newer schema, but rely on that only when the release’s notes below say so.

ocidex migrate down exists for development. It is not a supported rollback, because several of its steps lose data on purpose.

Per-version notes

Section titled “Per-version notes”

Newest first. Each entry names the issue that made the change.

Next release (unreleased)

Section titled “Next release (unreleased)”

Behavior changes to check after upgrading:

  • snake_case query parameters are no longer accepted (ocidex-6hfs). Through 1.0 the server translated the pre-1.0 spellings (?subject_version=, ?sort=cvss_score) to their camelCase names, as announced in the 1.0 notes. That translation is gone: a snake_case parameter is now ignored like any other unknown one, so a filter silently stops filtering and an ingest parameter such as subject_name is dropped. What to do: upgrade any CI image or script that pins an ocidex-cli older than 1.0, and rename parameters in your own API calls to camelCase (subjectVersion, sort=cvssScore).
  • Response $schema links moved under /api (ocidex-m3yn). Every JSON body’s $schema, and every error’s Link: rel="describedBy" header, now points at /api/schemas/<Name>.json instead of /schemas/<Name>.json. The old path was not routed to the API on a standard install, so those links led to the web app; now they resolve. /schemas/<Name>.json on the API itself redirects to the new path. Nothing to do unless you compare $schema values literally.

Deprecations (removed in 2.0):

  • ENRICHMENT_WORKERS and ENRICHMENT_QUEUE_SIZE (ocidex-lwow). Neither has done anything since the job queue moved to the database; they were only echoed on the admin Status page. The server and every worker now log a warning at startup when either is set, the Status page no longer shows them, and enrichment.workers and enrichment.queueSize in GET /api/v1/admin/status are marked deprecated. What to do: remove both from your environment or Helm values. To change enrichment concurrency, set ENRICHMENT_MAX_CONCURRENCY on the enricher workers.

1.0.0

Section titled “1.0.0”

After upgrading:

  • Run ocidex migrate backfill once to clean up stored licenses (ocidex-wb5k). Ingest now splits license expressions, maps aliases such as Debian’s Expat to MIT, and drops fragments like AND or a sha256: digest (ocidex-nps9.13), but only for SBOMs ingested from now on. The backfill’s two new steps apply the same rules to the licenses already stored. The first re-derives every license stored without an SPDX id, moving its components to the licenses it really names and deleting the old row. The second reads the CycloneDX license expressions that older ingest ignored and adds the licenses they name. Both are idempotent, and a second run reports nothing to do. License counts catch up on the next rollup refresh.

Behavior changes to check after upgrading:

  • Every /api/v1 JSON field is camelCase (ocidex-nps9.32, decided in ocidex-nps9.7). The admin, auth, cluster, discovery, job, namespace, registry, source, stats and status endpoints returned and accepted some snake_case fields; each is renamed by the same rule (artifact_count → artifactCount), in responses and in request bodies. Query parameter names and sort keys follow the same rule (ocidex-nps9.34): ?subject_version= is now ?subjectVersion=, ?sort=cvss_score is ?sort=cvssScore. The server still accepts the old query spellings through 1.0 and drops that in the next release (ocidex-6hfs), so a CI image pinning an older ocidex-cli keeps ingesting correctly; bump it before then. Bookmarked cluster pages that filter with ?k8s_namespace= or ?match_state= open unfiltered; the page now uses ?k8sNamespace= and ?matchState=. What to do:

    • Upgrade the k8s agent, the operator and ocidex-cli together with the server. They talk to the API through pkg/client, and a version older than the server sends the old names: the agent’s inventory push (POST /api/v1/clusters/{id}/inventory) is rejected until the agent is upgraded, so cluster inventory pauses for that window.

  • Every running image in a registered cluster is ingested (ADR-0044 K10, ocidex-ve0f).   • In production, OIDC_ISSUER_URL must be https (ocidex-vvw6.3). With ENVIRONMENT=production the API refuses to start with a plain-http issuer. OIDC requires https, and the rule keeps the demo’s mock issuer out of a real installation. GitHub-only installs are unaffected.

0.2.0

Section titled “0.2.0”

Behavior changes to check after upgrading:

  • Registry responses no longer carry owner_id or owner_username (ocidex-bt62.2). A registry has no owner of its own; it belongs to a namespace (ADR-039, ADR-046). The two fields only repeated the namespace’s owner member, and only the list endpoint filled in owner_username. Read the owner from the registry’s namespace (GET /api/v1/namespaces/{id}, ownerId / ownerUsername). /api/v1/users/me/registries still lists registries in namespaces you own.

  • The account migration 00008 seeded is removed if it was never used (ocidex-7tss). Migration 00080 deletes the GitHub 16961380 account (a viewer since 0.1.0) unless it has ever signed in or has a session, API key, namespace membership, watch, email or second identity. A fresh install now starts with no accounts. If the account was used on your install, nothing changes.

After upgrading:

  • Run ocidex migrate backfill once if your database predates 0.1.0’s data (ocidex-bt62.1). The one-shot backfill-flavor, backfill-component-purl and backfill-provenance binaries are gone, and ocidex migrate backfill replaces them. It fills the columns ingest now writes for rows stored before it did: an SBOM’s flavor, a component’s purl version (until then the component is never vulnerability-scanned), and component provenance plus file_path (until then ADR-048 command relationships miss those SBOMs). It is idempotent and a no-op on a fresh install. It reads every affected SBOM’s raw_bom, so it is not part of the chart’s migrate hook. See Backfilling rows stored before ingest derived them.

0.1.0

Section titled “0.1.0”

Before upgrading:

  • Add the credential encryption keys (ocidex-d90k, ADR-051). Add DATA_ENCRYPTION_KEYS=<id>:<base64 32 bytes> and DATA_ENCRYPTION_ACTIVE_KEY=<id> to the chart’s existingSecret. With ENVIRONMENT=production (the chart default), the API, the scanner worker, the enrichers and the migrate Job refuse to start without them. Generate a key with openssl rand -base64 32 and back it up separately from the database. Losing it means re-entering every registry credential. The migrate hook runs ocidex migrate encrypt-secrets after migrate up and encrypts existing plaintext. Plaintext rows keep working until it runs. See Rotating the credential encryption key.
  • Set BOOTSTRAP_ADMINS (ocidex-avsz.1). Migration 00008 made GitHub user 16961380 an installation admin in every database. Migration 00079 demotes that account to viewer unless it has a session or an API key. The first admin now comes from BOOTSTRAP_ADMINS (chart: api.env.bootstrapAdmins) and is promoted at sign-in. Set it before upgrading if you sign in as that account, or as any other admin you still need. See The first admin.
  • Cross-site SPA deployments: set SESSION_COOKIE_SAMESITE=none (ocidex-mqav.2). The session cookie is now SameSite=Lax in production. It was SameSite=None. Lax works whenever the SPA and the API share a registrable domain. If you serve the SPA from a different registrable domain, set SESSION_COOKIE_SAMESITE=none (chart: api.env.sessionCookieSameSite), or every API call from the SPA arrives without its session.
  • Scanning a registry on a private network: set the egress policy (ocidex-avsz.5, .6, .7). The API, scanner-worker and the enricher workers now refuse to dial private addresses (10/8, 172.16/12, 192.168/16, 100.64/10, fc00::/7), loopback, link-local (including cloud metadata) and multicast. That covers an in-cluster or LAN registry such as zot or Harbor. Its scans fail as permanent errors, and the API rejects an ingested SBOM naming an image there with 400. Before upgrading, allow just that registry’s address with EGRESS_ALLOW_CIDRS (chart: egressGuard.allowCidrs), or all private ranges with EGRESS_ALLOW_PRIVATE=true (chart: egressGuard.allowPrivate). Set the same values on every component; the chart does. See Egress policy.
  • CORS_ALLOWED_ORIGINS must be exact origins in production (ocidex-mqav.3). With ENVIRONMENT=production, the API refuses to start if CORS_ALLOWED_ORIGINS contains *, or any entry that isn’t scheme://host[:port] (http or https, with no path, trailing /, credentials, query or fragment). Check the value before upgrading.
  • Behind an ingress: set TRUSTED_PROXY_CIDRS (ocidex-mqav.5). Sign-in endpoints are rate-limited per client IP: 30 requests per minute by default (AUTH_RATE_LIMIT, chart api.env.authRateLimit; 0 disables). Set TRUSTED_PROXY_CIDRS (chart api.env.trustedProxyCidrs) to the ingress’s address range, or every visitor shares the ingress’s budget. If that range is not fixed, TRUSTED_PROXY_HOPS (1 for a plain ingress) or CLIENT_IP_HEADER need no addresses; read their caveat in Client IPs behind a proxy first (ocidex-w6st).

Behavior changes to check after upgrading:

  • Cookie-authenticated writes must come from a trusted origin (ocidex-mqav.1). A POST, PUT, PATCH or DELETE that authenticates by session cookie is refused with 403 unless its Origin (or Referer) is one of:

    • in CORS_ALLOWED_ORIGINS;
    • FRONTEND_URL, when CORS_ALLOWED_ORIGINS is unset;
    • the API’s own origin (API_BASE_URL).

    API-key clients are unaffected.

  • SBOM ingest and the expensive reads are rate-limited per principal (ocidex-mqav.6). The default is 120 requests per minute each (API_RATE_LIMIT_INGEST, API_RATE_LIMIT_HEAVY; 0 disables). No role is exempt, so raise the ingest limit if a CI or operator key pushes faster.

  • Registry URLs are validated on create and update (ocidex-avsz.8). A registry url must be host[:port] (or http(s)://host[:port]). Credentials, a path, a query or a fragment are rejected with 422, and so is an IP address the egress policy refuses. Registries created before the upgrade keep working, but editing one with such a URL fails until the URL is fixed. Put repositories in repositories, not in the path, and credentials in auth_username / auth_token.

  • Attaching a new registry to an existing namespace needs manage_source there (ocidex-avsz.2). POST /api/v1/registries with a namespace that already exists now returns 404 to non-members and 403 to members without manage_source, instead of attaching the registry. Naming a new namespace still creates it.

  • The web UI sends a strict Content-Security-Policy (ocidex-mqav.7, .9). The bundled nginx sets frame-ancestors 'none', so the UI can no longer be embedded in an iframe. Scripts and styles load only from the UI’s origin, plus Google Fonts. A proxy that injects scripts or inline styles into the UI’s pages will have them blocked.

  • New, optional: who may sign in and create namespaces (ocidex-avsz.4). SIGNUP_MODE (default open, the previous behavior) and SELF_SERVICE_NAMESPACES (default true) let you limit sign-in to existing accounts and keep global viewers from creating namespaces. Nothing changes unless you set them. See Who may sign up.

Chart rollback without a restore: not safe for this release. Migration 00079 demotes the seeded admin, and the previous version does not read BOOTSTRAP_ADMINS.
