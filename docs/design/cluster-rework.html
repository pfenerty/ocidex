Cluster agent rework: flows and mockups

One design for the whole cluster feature, built from the 25 audit findings in ocidex-70eo.1. It covers connecting a cluster, the cluster list, cluster detail, where clusters appear across the app, and decommissioning. The backend this depends on has already landed on the epic branch: agent self-reporting (.3), cluster-bound credentials (.5) and the health model (.4).

Purple tags like this name the audit findings each choice answers.

Principles

  1. One state drives every surface. Health (never_reported, healthy, stale, erroring) and its reason come from the server, and every page shows the same pill and reason. Nothing works out staleness for itself.
  2. No data is not zero. Before the first accepted snapshot, a cluster has no coverage band, no tabs with empty tables, and no zero tiles. It shows how to connect it. D3 D4 R4
  3. Pages wait live. Any page showing a cluster that is waiting or erroring polls every 5s. A healthy cluster polls every 30s. Nobody reloads to find out whether a fix worked. D5 P2
  4. The credential belongs to the cluster. Keys are minted, shown once, rotated and revoked from the cluster. Nobody has to visit API keys to connect a cluster. D1 D2 D6
  5. Clusters are context, not an island. Wherever OCIDex shows an image, it says whether that image is running and where. F1 F2 F3

What happens next

OCIDex creates the cluster and an agent credential that can push this cluster's inventory and do nothing else. You get one command to run against the cluster. This page then waits for the agent's first report.

The agent reads pods only. It needs no CRDs, and OCIDex stores no kubeconfig.

What implementation needs that does not exist yet

  • Chart: apiKey.value creates the Secret, and apiKey.existingSecret keeps today's behaviour (.6).
  • API: one endpoint that creates a cluster and its first credential together, so step 1 can't leave a cluster with no key (.6). Coverage counts and running criticals on ListClusters (.7). Running workloads by artifact, and a per-user cluster rollup (.8). Whether this deployment can scan, so Gaps can say so instead of showing a 503 (.12).
  • server.url: the API's public URL, from config. window.location.origin is wrong whenever API_BASE_URL differs from the web origin (D7).
  • Polling: TanStack refetchInterval set from health, 5s while waiting or erroring and 30s otherwise. No websockets.

Decisions to review

Q1. Connect on a page, not in a modal.Recommended: a page. It shows a one-time key and then waits, and a modal is too easy to dismiss at either step.
Q2. A new Agent tab.Recommended: yes. Credentials, push history, settings and delete are all about operating the agent, and today they're split between the list row, the Overview and API keys.
Q3. The key in --set apiKey.value.It ends up in the Helm release, which Helm stores as a Secret in that namespace. That's the same blast radius as the Secret it replaces, but it also appears in shell history. Recommended: helm --set as the default, plus a values.yaml / existingSecret option for GitOps.
Q4. A segmented bar instead of four tiles.Recommended: yes. It shows proportion, which four separate numbers don't, and it stops looking like four selected tabs. Clicking a segment still filters Workloads.
Q5. Health thresholds.Stale after 3× the reported interval, and erroring as soon as one push is refused after the last success. One bad push is enough because refusals don't fix themselves: a 401 stays a 401.
