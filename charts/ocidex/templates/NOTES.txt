=== Prerequisites ===

The application requires a Secret named "{{ .Values.existingSecret }}" containing:
  - DATABASE_URL      (PostgreSQL connection string, e.g. postgres://user:pass@host:5432/db)
  - SESSION_SECRET    (random 32-byte hex: openssl rand -hex 32)
  - at least one identity provider, either or both of:
      GITHUB_CLIENT_ID + GITHUB_CLIENT_SECRET   (GitHub OAuth app)
      OIDC_ISSUER_URL  + OIDC_CLIENT_ID         (any OIDC issuer)

The API refuses to start with no provider configured. Setting only one half of the
GitHub pair is a startup error, not a silent disable.

Create it with (GitHub shown; swap in the OIDC keys for an OIDC-only install):

  kubectl create secret generic {{ .Values.existingSecret }} \
    --namespace {{ .Release.Namespace }} \
    --from-literal=DATABASE_URL=<your-postgres-url> \
    --from-literal=GITHUB_CLIENT_ID=<client-id> \
    --from-literal=GITHUB_CLIENT_SECRET=<client-secret> \
    --from-literal=SESSION_SECRET=$(openssl rand -hex 32)

See docs/CONFIGURATION.md for the full list of supported fields.

=== Upgrading from a release before NATS ran as non-root ===

  NATS now runs as uid {{ $natsUID }} so the chart satisfies the
  PodSecurity "restricted" profile. A JetStream store written by an older
  release is mode 0700 root:root, and fsGroup does not fix it on a hostPath- or
  NFS-backed StorageClass — the kubelet only applies fsGroup to volume types
  that support ownership management. NATS would come up and die with:

    [FTL] Can't start JetStream: storage directory is not writable

  Recreate the volume once, before or during the upgrade:

    kubectl -n {{ .Release.Namespace }} scale statefulset {{ include "ocidex.fullname" . }}-nats --replicas=0
    kubectl -n {{ .Release.Namespace }} delete pvc data-{{ include "ocidex.fullname" . }}-nats-0
    kubectl -n {{ .Release.Namespace }} scale statefulset {{ include "ocidex.fullname" . }}-nats --replicas=1

  Then restart the API and workers, so they re-provision the stream and their
  durable consumers:

    kubectl -n {{ .Release.Namespace }} rollout restart deploy -l app.kubernetes.io/part-of=ocidex

  That second step is required, not optional: the stream is created by
  CreateOrUpdateStream at process startup, and a client that merely *reconnects*
  to the rebuilt server never re-runs it. Until the restart, hint delivery is
  dead — though no work is lost, because the workers keep claiming jobs on their
  DB poll interval.

  Wiping the store is safe. It is a doorbell cache, not the queue of record:
  scan and enrichment jobs live in Postgres (ADR-024), so at worst a job waits
  one poll interval instead of being picked up instantly. Fresh installs need no
  action.
{{- end }}
